------------------------------------------------------------------------
1. WHAT THE PROJECT IS FOR
------------------------------------------------------------------------
Domain: home loans (mortgages). A loan packet is ONE PDF holding many
documents for one borrower: loan application, pay slips, bank statements,
tax forms, Loan Estimate / fee sheet, title report, IDs.

The classifier's 15 types were already a mortgage-file taxonomy (Mortgage,
Lender Fee Sheet, Pay Slip, Bank Statement, Preliminary Title Report, ...),
and the eval packet was a 50-page, 21-document mortgage packet.

Problem it solves: a reviewer needs specific facts out of a long packet.
Generic "chat with PDF" tools fail here by inventing or rounding numbers,
mixing up documents ("amount" is on several), breaking tables, and giving
answers you cannot check. This app splits the packet into documents,
extracts tables faithfully (Textract), searches keyword + semantic, and
cites the document type and page.


------------------------------------------------------------------------
2. HOW A LOAN OFFICER WOULD USE IT (workflow discussion)
------------------------------------------------------------------------
- One chat = one PDF = one borrower's packet. Ten borrowers = ten chats.
- Uploads are batch-friendly: drop all packets, the worker processes them
  2 at a time in the background [v012]. Questions are one borrower at a
  time; chats never see each other's data.
- Limits noted: DAILY_MESSAGE_CAP=5 (owner's own cap, kept deliberately),
  RATE_UPLOAD 10/hour, MAX_UPLOAD_MB=3, no cross-borrower questions.

"Stare and compare": the application holds the borrower's CLAIMS (income,
employer, assets, declarations); the supporting documents are the EVIDENCE.
Verification = checking claims against evidence.

What the app did at this point: find and cite each value on request. The
officer asked, read both answers, and compared them herself. The 250 eval
questions were all single-fact lookups; none compared anything.

How lenders actually verify (general practice):
  1. data straight from the source (tax transcripts, employment/bank
     verification services; in India: Account Aggregator, EPFO, e-KYC)
  2. document AI with FIELD extraction into the loan system + rules
  3. automated underwriting engines
  4. a human underwriter signs off on exceptions
Where a GenAI copilot fits: beside that pipeline, not replacing it —
answering off-checklist questions in long unstructured documents (title
reports, contracts), explaining flags, drafting follow-ups.

------------------------------------------------------------------------
10. CHAT vs AUTOMATIC REVIEW — THE DESIGN DECISION
------------------------------------------------------------------------
Chat alone depends on the officer asking the right question, is not
repeatable across officers, and costs 2 questions per check. Lender
copilots are built in layers:
  1. classify + split pages ............................ already built
  2. extract a FIXED set of fields per document type ... new
  3. compare with RULES in plain code (not the LLM) .... new
  4. review screen: ✅/❌/⚠️ with both sources .......... new
  5. chat on top, for everything off-checklist ......... already built
A human makes the final call throughout.

11. EXTRACTION OPTIONS — RESEARCH (AWS pricing page + developer guide)
------------------------------------------------------------------------
Textract per page (first 1M pages, AWS worked examples):
  Detect text $0.0015 · Tables $0.015 · Forms $0.05 · Tables+Forms $0.065
  Tables+Queries $0.020 · Analyze Lending $0.07 · Analyze Expense $0.01

FINDING 1 — our cost figures were ~4x too low. The code calls TABLES+FORMS
($0.065/page); docs assumed $0.015. 50-page packet ~$3.25 (not ~$0.75);
7-page calibrate ~$0.46 Textract; 8-page Whitfield packet ~$0.52.
(README / CLAUDE.md / roadmap cost lines still need correcting.)

FINDING 2 — FORMS (77% of the Textract bill) returns label->value pairs
(KEY_VALUE_SET blocks) that the code requested, paid for, and discarded.

Analyze Lending (dedicated mortgage API), checked against AWS's keys.csv:
  + classifies ~36 US mortgage doc types; 1003 has 253 fields (income,
    employer, assets, liabilities, declarations); PAYSLIPS 22 fields
  - BANK_STATEMENT is summary-only (14 fields): no transactions, so it
    cannot surface a single large deposit
  - no Loan Estimate, no title report; US documents only (no Form 16/ITR/PAN)
  - async only, PDF must be in S3; returns fields not text, so RAG would
    still need normal Textract (supported pages paid twice)
Options: A) use the FORMS pairs we already pay for; B) drop FORMS, use
Queries ($0.020); C) Analyze Lending; D) LLM with a fixed schema.
DECISION: A + D. Not Analyze Lending (for now). Keep FORMS.

12. THE AUTOMATIC FILE REVIEW — IMPLEMENTATION                      [v012]
------------------------------------------------------------------------
Flow: upload -> ingest -> chat "ready" -> review runs -> panel appears.

backend/core/pdf_processor.py  [both — the FORMS part is useful anywhere]
  - Textract KEY_VALUE_SET pairs kept per page (type "kv"), NOT indexed
    (same words are already in the text). Each page's own classification
    kept too (page_type), for the review.
backend/core/models.py  [both]
  - PageInfo.kv, PageInfo.page_type; LogicalDocument.kv, .page_types
backend/core/review.py  [NEW]
  - SCHEMAS: fixed fields + list fields for Loan Application, Pay Slip,
    Bank Statement, Lender Fee Sheet, Preliminary Title Report.
  - Fields filled first from FORMS pairs (synonym map), then ONE flash-lite
    call per document for missing fields and lists (deposits, debits,
    liabilities, liens, easements).
  - Grounding guard: an LLM value is kept only if its exact text is found in
    that document; the PAGE is located in code, never taken from the model.
  - Lien "payoff required" decided from the report's own words near the
    amount; a "lien" without an amount is dropped.
  - Rules (plain Python, thresholds at the top: income 5%, balance 10%,
    large deposit 25% of monthly income): income (pay frequency from the
    slip or from period dates), employer, checking balance, payroll deposits
    vs net pay, large non-payroll deposits vs declaration, loan amount and
    price vs Loan Estimate, stated debts appearing as debits (amount, or
    creditor name when paid above the minimum), title liens and easements,
    missing required documents.
  - Statuses: mismatch / review / missing / match / info, each with both
    sides' value and page.
  - Splits a merged document for the review where a page's own type is a
    different reviewable type (search grouping untouched).
  - Malformed model JSON: repaired, then one retry.
  - Self-test: `python backend/core/review.py` (no network) — added to CI.
backend/worker.py  [v012]
  - After "ready", _run_review(); a review failure is stored as status
    "failed" and NEVER fails or retries the ingest.
backend/db/models.py, migrations.sql, main.py
  - New JSONB column drs_chat_sessions.review; ensure_columns() adds it at
    API/worker startup (idempotent). Returned with GET /api/chats/{id};
    reset on re-upload.
frontend/src/ChatPanel.jsx, App.css
  - "File review" panel above the chat: status per check, value + page
    chips, "Ask" button fills the chat box; polls while the review runs.
Cost per packet: ~5 flash-lite calls (~1k tokens each), fractions of a cent.

19. ACTING ON A FLAG — OFFICER DECISIONS + AUDIT TRAIL          [both]
======================================================================
What: every mismatch/review flag gets "Accept" (explained; a NOTE IS
REQUIRED) or "Confirm issue". Each call shows "Accepted by <user> ·
<time>" plus the note, and a per-flag History list. The sidebar badge
counts OPEN flags: "2 open · 1 resolved", then "✓ reviewed".

Files:
- backend/db/models.py: new table ReviewDecision (drs_review_decisions):
  chat_id, run_id, check_key "{check.id}:{index}", check_label snapshot,
  decision accepted|confirmed, note, user_id, username, created_at.
  APPEND-ONLY: a changed mind is a new row; the latest row per flag is
  the current state. Created by create_all (new table).
  ensure_columns() also backfills a run_id onto old finished reviews.
- backend/worker.py: _run_review stamps review["run_id"] = uuid hex.
  Decisions attach to a run, so a RE-UPLOAD (new review) starts with
  every flag open; old decisions remain in decision_history.
- backend/main.py:
  POST /api/chats/{id}/review/decisions {check_key, decision, note}
    404 not your chat (_owned_chat), 409 no finished review,
    422 unknown flag / accept without note, 201 -> {decision}.
  GET /api/chats/{id} adds chat.decisions (latest per flag, this run)
    and chat.decision_history (all rows).
  _review_summary adds open / resolved; list_chats loads decisions for
    all listed chats in ONE query (_decisions).
  Deleting a chat does NOT delete its decisions (audit trail).
- backend/migrations.sql: CREATE TABLE drs_review_decisions.
- frontend/src/api.js: decideFlag(id, check_key, decision, note).
- frontend/src/ChatPanel.jsx: FlagDecision component inside each flag
  row; ReviewPanel takes decisions/history/onDecide and shows
  "n/m decided" in the headline; state reset on chat switch/re-upload.
- frontend/src/App.jsx: ReviewBadge uses open/resolved.
- frontend/src/App.css: .flag-* styles.

Verified (v012): eslint, vite build, ruff, review selftest; endpoint
test against Neon with the Whitfield file: 3 open -> accept-without-
note 422, unknown flag 422, other chat 404, confirm then accept 201,
latest = accepted, history 2, badge 2 open · 1 resolved. Test rows
deleted afterwards.

Porting to main: same code; main has no worker, so stamp run_id where
